## 功能代码路径与确定性核对（重点）

**问：视频拼接是否确定性？答：不是纯本地确定性拼接，而是「确定性指令 + 非确定性上游生成」。**

- 本地确定性部分（`registry/video-concat.ts`）：
  - 时长求和 `effectiveVideoConcatSeconds`、裁剪区间 `trimVideoConcatClip`、字段装配 `buildVideoConcatFields` 都是纯函数（模块头注释：「本模块不谎称调用了模型：所有函数都是本地确定性计算」，`registry/video-concat.ts:15`）。
  - `buildVideoConcatPrompt`（:412）把「片段顺序 / 裁剪区间 / 比例 / 目标时长 / 封面」写成确定性指令交给 provider。
- 非确定性部分：
  - 真正产出视频仍走模型（prompt + 多段 video[]）。页面自己的通道说明写着：「OpenAI /videos 通道会把每段视频作为 video[] 上传；**多段是否被上游采用仍取决于中转实现**。」
  - 即：本地**不做 ffmpeg 拼接**，没有帧级/时间轴级的确定性合成能力；成片由上游模型重生成，可能出现重绘、丢片段、时长不符。
- 阻断设计（`registry/video-concat.ts:563-572` + `adapters/video-concat.ts:148-180`）：`multiReference` 能力必须为 `supported`，否则 `blocked=true`（gemini 只取 `videos[0]` 会静默丢片段 → 阻断）。当前页面显示「通道 openai · 多段视频 **已验证发送**」，说明走的是被认定支持多段的 openai 通道。
- 片段数量：`VIDEO_CONCAT_MIN_CLIPS=2`、`VIDEO_CONCAT_MAX_CLIPS=10`（registry），但页面文案写「支持选择 2~4 个视频素材」——**页面文案与 registry 上限不一致**（见差异 3）。
- 字段落位：`editType / imageFormat / imageHeight / imageSize / imageUrl / imageWidth / videoCoverUrl / videoList / videoRatio / videoTime` 共 10 个字段一次落齐（`buildVideoConcatFields`），`auditVideoConcatFields` 逐字段核对防静默丢参。

## 结论

- 布局与配置区最接近原站（一屏容纳、比例 4 选一、底部主按钮）；但**「确定性」是伪命题**：本地只保证字段与提示词确定性，成片由上游模型重生成，页面自己也承认多段是否被采用「取决于中转实现」。
- 封面必填（原站无）与片段数文案（2~4 vs 实现 10）是两处需要修正的不一致。
- 本轮未提交拼接，功能判定 NOT_RUN。
