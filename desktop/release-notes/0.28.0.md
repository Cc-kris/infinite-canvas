## 0.28.0 修复：桌面版一启动就崩；生图慢的真正原因

**一、打包版客户端一启动就白窗、连不上 Agent（本轮最重要）**

上一版打出来的安装包，双击之后只弹一个信息为空的窗口，代理没起、Agent 连不上、
什么功能都用不了。原因是打包清单（`build.files`）是白名单，里面漏了
`agent-plugin.js` 和它依赖的 `agent-detect.js`——主进程一加载就报
`ERR_MODULE_NOT_FOUND`，而打包版没有终端，错误只变成那个空白弹窗。

现在两个文件都进了打包清单，并用实际打出来的应用跑通验证：窗口正常、
代理自起、真实生图返回 200。

顺手补了一个排查入口：主进程遇到 `uncaughtException` / `unhandledRejection`
会先把完整堆栈写进 `main-errors.log`（在应用的 userData 目录里），再照旧弹窗。
以后再出现「装到别的机器上就起不来」，日志是现成的。

**二、生图要等好几分钟，慢在出口线路**

之前一直以为是模型慢、上游排队。实测下来都不是：独立运行的 `canvas-proxy`
用 Node 的 `fetch` 直连，**完全不看系统代理**，而这条直连线路下载大响应会被
限速到约 30 KB/s。一张 1K 图约 2 MB——生成其实 20 秒就完了，结果却要多等
60~75 秒。

同一个请求对照：直连 92.5 秒，走系统代理 22.5 秒。现在代理启动时会自己探测
系统代理（环境变量 → macOS `scutil --proxy` → Windows Internet 选项），探到就
带着 `NODE_USE_ENV_PROXY=1` 重启自己走代理，直连留作第二通道兜底。真实验证：
23.1 秒拿到 1.86 MB 图片。

**三、「要不要走代理」两端终于用同一份判定**

网页版和桌面客户端此前各写一套逻辑，容易出现「一端说走了代理、另一端其实没走」。
现在统一在 `canvas-proxy/system-proxy.js` 里判定：桌面端起代理前先探测系统代理，
没探到就只挂直连通道，不再宣称一条机器上并不存在的跳转。

`GET /` 新增 `route` 字段，报告最近一次请求实际走的通道（`system` / `direct`），
两端都能自证。想强制直连可以设 `CANVAS_PROXY_DISABLE_SYSTEM_PROXY=1`。

**四、网页版不用再手动开代理**

`vite` 启动时如果 `127.0.0.1:23210` 没人监听，会自己拉一个本地转发代理；
已经有人在跑就直接复用。关掉 dev server 时代理一起收尾。
第一跳（浏览器 → 本机代理）和第二跳（本机代理 → 上游）现在都是默认生效的。
